claude-mini: how the backend actually works

Not a file tour. This is the design — what an agent is, how the API call is shaped, what every AI term means, and where each idea lives in our system.

~3,750 lines of Go · one HTTP endpoint · eight tools · zero frameworks

Read this first

There is exactly one idea in this entire project. Everything else is plumbing around it:

A language model cannot do anything. It can only produce text. So we let it produce text that describes an action, we perform that action ourselves on the real machine, we paste the outcome back into the conversation, and we ask it again. Loop until it stops asking.

That loop is the agent. Everything below is detail.

01What an "agent" really is

In the AI world people use the word agent for something surprisingly small. It is not a neural network, not a service, not a personality. An agent is a control loop wrapped around a chat model.

         ┌─────────────────────────────────────────────────────┐
         │                                                     │
         │   1. send the WHOLE conversation to the model       │
         │                       │                             │
         │                       ▼                             │
         │   2. model replies with EITHER                      │
         │        (a) plain text   ───────────► stop, print it  │
         │        (b) a tool call  ──┐                         │
         │                           │                         │
         │                           ▼                         │
         │   3. WE execute that tool on the real computer      │
         │                           │                         │
         │                           ▼                         │
         │   4. append the result to the conversation         │
         │                           │                         │
         └───────────────────────────┘
                    (go back to step 1)

That is literally Agent.Run(). The for { … } loop in internal/agent/agent.go is the agent. Delete the loop and you have a chatbot. Keep it and you have a coding assistant.

Terminology you should use

Agentic loop / ReAct loop — the cycle above. "ReAct" = Reason + Act, from the 2022 paper that named the pattern: the model alternates between reasoning in text and taking actions in the world.

Turn — one trip around the loop: one API call plus the tools it triggered. Our Cost.Turns counts these.

Task — everything from the user pressing Enter until the model replies with no tool calls. One task = many turns.

Harness / scaffold — the code around the model. That is our whole Go program. The industry phrase is: the model is the engine, the harness is the car.

Inner loop / outer loop — inner = tool-call iterations within one task; outer = the human typing the next task.

Why the harness is the product

Two systems using the identical model behave wildly differently based on the harness. Ours decides:

  • Which tools exist — the model can only do what we hand it.
  • What goes back into context — we clamp tool results at 24 KB so one giant file doesn't poison every later turn.
  • What needs a human — our permission gate.
  • When to stop — no tool calls means done.
  • What survives — compaction, transcripts, undo.

Model quality sets the ceiling. Harness quality decides how close you get to it.

02The model is stateless — this changes everything

The single most misunderstood fact about LLM backends: the model remembers nothing. There is no session on the server. Every HTTP request is a cold start.

When you send turn #7 you are not sending "the next message". You are re-sending turns 1 through 6 plus the new one, every single time. The illusion of memory is created entirely by our client re-uploading history.

  Turn 1  POST →  [system, user]
  Turn 2  POST →  [system, user, assistant, tool, user]
  Turn 3  POST →  [system, user, assistant, tool, user, assistant, tool, user]
                   └─────────────── re-sent in full, every time ──────────────┘

In our code that growing array is one struct field:

type Agent struct {
    history []llm.Message   // ← THIS is "the memory". Nothing else is.
    …
}

Three consequences fall out of this, and three parts of our design exist only to answer them:

ConsequenceWhy it happensOur answer
Cost grows quadraticallyTurn N re-bills every earlier tokenCost tracker + result clamping
Context runs outFixed token ceiling per modelmaybeCompact() at 60k
History must stay structurally validAPI rejects a malformed message sequenceInterrupt + resume repair logic
Terminology

Context window — the max tokens the model accepts in one request (system + history + new message + room for the reply). 128k / 200k / 1M depending on model.

Stateless inference — the server keeps nothing between calls. Conversation state lives 100% on the client. That's us.

Prompt caching — a provider optimization where an unchanged prefix of your messages is cached server-side so the re-send costs a fraction of face value. We now support this as an opt-in (CLAUDE_MINI_CACHE=1) — see §15.

Notice what is not in that diagram: no database, no vector store, no message queue, no orchestration framework. A loop, an HTTP client, and a map of function pointers.

04The API call itself

internal/llm/client.go

We speak the OpenAI Chat Completions protocol. This matters enormously: it is the de-facto standard, so the same client code reaches OpenAI, OpenRouter, DeepSeek, Groq, Together, vLLM, LM Studio and a local Ollama. We wrote one client and got every provider.

The request body

POST {baseURL}/chat/completions
Authorization: Bearer {apiKey}
Content-Type: application/json
Accept: text/event-stream

{
  "model":       "deepseek-v3",
  "messages":    [ …the entire history… ],
  "tools":       [ …8 JSON-Schema tool definitions… ],
  "tool_choice": "auto",
  "stream":      true,
  "stream_options": { "include_usage": true },
  "temperature": 0.3
}

The four message roles

Every entry in messages has a role. There are exactly four, and each means something precise:

RoleWho writes itPurpose
systemUs, once at startupStanding instructions. Highest authority. Index 0, never removed.
userThe humanThe task, plus any @file attachments we inlined.
assistantThe modelIts prose reply and/or its tool_calls.
toolUs, after running a toolThe tool's output, tagged with tool_call_id so the model knows which request it answers.
The invariant that will bite you

Every tool_call in an assistant message must be followed by a matching tool message with the same tool_call_id. If even one is missing, the API rejects the entire next request with a 400 — forever, because the bad history gets re-sent every turn.

This one rule is why our interrupt handler still emits "[interrupted by user before this tool ran]" for tools that never executed, and why Resume() drops a dangling final assistant turn. Both exist purely to protect this invariant.

Temperature

We hardcode 0.3. Temperature controls the randomness of token sampling: 0 is near-deterministic (always the most likely next token), 1.0+ is creative and wandering. For a coding agent you want low — you want the same tool call for the same situation, not variety. 0.3 leaves a sliver of flexibility so the model can escape a repetitive rut.

Sampling terminology

Temperature — flattens or sharpens the probability distribution over next tokens. top_p / nucleus sampling — sample only from the smallest set of tokens whose probabilities sum to p. top_k — sample only from the k most likely. Greedy decoding — always take the top token (temperature 0). Deterministic — same input, same output; even at temp 0 most providers don't fully guarantee it due to floating-point batching.

Retries

Stream() wraps streamOnce() with up to 4 attempts and linear backoff (2s, 4s, 6s). Two rules make it safe:

  • Never retry after emission. If a single token or tool-call fragment already reached the user, a retry would duplicate it. The emitted flag forbids it.
  • Never retry a 4xx. A bad key or malformed request will not fix itself. We mark those fatal — except 429 Too Many Requests, which is genuinely transient.

05Streaming & SSE — reassembling a reply from fragments

We request stream: true, so instead of one JSON body we get Server-Sent Events: a long-lived HTTP response where each line looks like data: {…} and the stream ends with data: [DONE].

Each chunk carries a delta — an increment, not a full state. Our job is to fold hundreds of deltas back into one coherent message.

 data: {"choices":[{"delta":{"role":"assistant"}}]}
 data: {"choices":[{"delta":{"reasoning_content":"The user wants"}}]}   ← thinking
 data: {"choices":[{"delta":{"reasoning_content":" a test, so I"}}]}
 data: {"choices":[{"delta":{"content":"I'll read"}}]}                  ← visible prose
 data: {"choices":[{"delta":{"content":" main.go first."}}]}
 data: {"choices":[{"delta":{"tool_calls":[{"index":0,"id":"call_a1",
              "function":{"name":"read_file","arguments":""}}]}}]}      ← tool call begins
 data: {"choices":[{"delta":{"tool_calls":[{"index":0,
              "function":{"arguments":"{\"pa"}}]}}]}                    ← args arrive
 data: {"choices":[{"delta":{"tool_calls":[{"index":0,
              "function":{"arguments":"th\":\"main.go\"}"}}]}}]}        ← …in pieces
 data: {"choices":[{"finish_reason":"tool_calls"}]}
 data: {"usage":{"prompt_tokens":2145,"completion_tokens":88}}          ← the bill
 data: [DONE]

Three separate streams are interleaved in those chunks, and we handle each differently:

Delta fieldWhat it isWhat we do
reasoning_contentThe model's private chain of thoughtCount its characters for the live token estimate; never stored in history
contentThe visible answerConcatenate into out.Content; print
tool_calls[]Function-call fragmentsAccumulate by index into a map, then flatten in arrival order

The tool-call accumulator

This is the subtlest code in the client. Tool calls arrive shredded: the id and name come in the first fragment, then the arguments JSON string dribbles in character by character across many chunks. A parallel multi-tool reply interleaves fragments for index: 0 and index: 1. So:

toolByIndex := map[int]*ToolCall{}   // keyed by delta index
var order []int                       // preserves first-seen ordering

// id/name: set once, when non-empty
if tcd.Function.Name != "" { tc.Function.Name = tcd.Function.Name }
// arguments: always APPEND — it is a partial JSON string
tc.Function.Arguments += tcd.Function.Arguments
Why arguments is a string, not an object

The API sends arguments as a JSON-encoded string, not a JSON object. That is deliberate: a partially-streamed object would be unparseable, but a partially-streamed string is just a shorter string. You concatenate first and json.Unmarshal only once the stream is complete — which is exactly what execTool does. This is also why a model that hallucinates malformed JSON produces a parse error we must feed back to it rather than a crash.

A 200 is not proof of success

One hard-won guard sits at the end of the read loop. Some gateways answer an unrecognized path with 200 OK and an ordinary JSON error body — AWS Bedrock does exactly this:

{"Output":{"__type":"com.amazon.coral.service#UnknownOperationException"},"Version":"1.0"}

With no data: lines to parse, the old code returned an empty assistant message. Empty message plus no tool calls is indistinguishable from "task complete", so the agent printed ✓ done for work that never happened. We now track whether any SSE frame was seen at all, and its absence is an error carrying a snippet of the body — plus, when the base URL ends in /chat/completions, the reason why. It is reported as non-retryable: a misconfigured URL will not fix itself in twelve seconds of backoff.

Interactive vs piped rendering

One nice design detail: in a real terminal we don't echo tokens as they stream. We only count them, so the animated spinner line ("✻ Brewing… 12s · 4.1k tokens · Esc to pause") can own the last line of the terminal without fighting streamed text for the cursor. Once the call returns and the spinner clears, we print the finished answer at once. When output is piped (CI, scripts), we fall back to true live streaming. Same backend, two presentation modes.

06The system prompt — programming in English

internal/agent/prompt.go

The system prompt is the closest thing an agent has to source code for its behavior. It is built once, at startup, and sits at history[0] forever. Nothing ever removes it — not even compaction.

Ours does four jobs. Recognizing these four categories is how you read or write any agent's prompt:

JobOur textTerm
Identity"You are claude-mini, a CLI coding agent…"Role / persona priming
EnvironmentWorking directory, OS, available tool namesContext injection / grounding
Policy"Explore before editing", "make minimal targeted changes", "if a tool errors, say what went wrong and correct"Behavioral constraints
Output contractEnd with DONE: … or BLOCKED: …Structured output / sentinel

The three lines that do the most work

// 1. Forces tool use over guessing — grounding
"Explore before editing: read files and search the codebase."

// 2. Prevents silent failure — the #1 agent failure mode
"If a tool returns an error, say briefly what went wrong and try a
 corrected approach. Never give up silently and never fabricate results."

// 3. Stops the loop from spinning forever
"When the task is complete, give a short summary.
 Do not call tools when no further action is needed."

Note how tightly the prompt is coupled to the harness. reg.Names() is interpolated into the prompt, so adding a tool to the registry automatically mentions it. And the prompt explicitly teaches the model about our permission system — "run_bash and run_server require the user's approval and may be declined; if declined, adapt rather than retrying the same thing" — because the model has no other way to learn that rule.

Prompt terminology

System prompt — standing instructions, highest priority. User prompt — the task. Prompt engineering — iterating on the wording to change behavior. Few-shot prompting — including worked examples (we use zero-shot: instructions only, no examples). Chain of thought (CoT) — "think step by step"; we ask for it explicitly, and reasoning models emit it in reasoning_content. Grounding — forcing answers to come from real observed data rather than model memory; our whole tool layer is a grounding mechanism. Hallucination — confidently stating something false; "never fabricate results" is our direct countermeasure. Prompt injection — untrusted text (a file, a web page) containing instructions the model then follows; every file we read is an injection surface, and our permission gate is the main mitigation.

A second, hidden system prompt

Compaction (§10) builds its own tiny prompt with a completely different persona: "You compress a coding agent's conversation history into a concise progress note…". This is a common pattern — one program, several prompts, each a small single-purpose "sub-agent" made of nothing but words.

07Tools / function calling — how text becomes action

internal/tools/tools.go

Function calling (newer name: tool use) is the mechanism that turns a text generator into an actor. It works in three beats.

Beat 1 — we advertise capabilities as JSON Schema

On every request we send a tools array. Each entry is a name, a natural-language description, and a JSON Schema for its arguments:

{
  "type": "function",
  "function": {
    "name": "edit_file",
    "description": "Make a targeted edit by replacing an exact string…",
    "parameters": {
      "type": "object",
      "properties": {
        "path":        {"type":"string", "description":"file path to edit"},
        "old_string":  {"type":"string", "description":"exact text to find"},
        "new_string":  {"type":"string", "description":"replacement text"},
        "replace_all": {"type":"boolean", …}
      },
      "required": ["path", "old_string", "new_string"]
    }
  }
}
The description IS the API contract

The model has never seen our Go code. The description string is the entire documentation it will ever get. This is why ours carry behavioral hints, not just definitions:

run_bash: "…Not for long-running servers — use run_server for those."
run_server: "…Returns immediately with the PID and a log path; it does NOT block. Use run_bash to read the log afterwards."
edit_file: "…old_string must appear exactly once unless replace_all is true."

Each of those sentences prevents a specific, observed failure. Writing tool descriptions is prompt engineering.

Beat 2 — the model emits a structured request

Instead of prose it returns tool_calls. It has not done anything; it has produced a JSON object saying what it would like done. Nothing happens yet.

Beat 3 — we execute and report back

execTool looks the name up in the registry, parses the arguments, optionally asks permission, runs the Go function, and pushes the output back as a tool message.

The most important line in execTool

Every failure path returns a string, never an error:

return fmt.Sprintf("Error: invalid JSON arguments: %v", err)
return fmt.Sprintf("Error: no such tool %q", name)
return "User declined this action. Do not retry it; consider an alternative."

An error is not a crash — it is feedback. The model reads "old_string appears 3 times; pass replace_all or add more context" and fixes its own call on the next turn. This is self-correction, and it is the difference between a demo and a tool people use. A harness that crashes on tool errors caps out at trivial tasks.

The Tool interface

Four methods, and the shape of them encodes our whole safety model:

type Tool interface {
    Def()      llm.Tool                              // schema sent to the model
    Mutating() bool                                // does it touch the real world?
    Preview(args)          (string, error)          // what the human sees BEFORE approving
    Run(ctx, args)         (string, error)          // do it; return text for the model
}

Mutating() + Preview() exist for exactly one reason: a human must be able to see and veto a side effect before it happens. That is the human-in-the-loop pattern (§9).

Tool terminology

Function calling / tool use — same thing, newer name. Tool definition / schema — the JSON Schema we advertise. Tool call — the model's request. Tool result / observation — what we send back ("observation" is the ReAct-paper word). tool_choice — "auto" (model decides, ours), "none" (forbid), "required" (must call something), or a named tool (force one). Parallel tool calls — several in one assistant message; we support this via the index-keyed accumulator and run them sequentially. MCP (Model Context Protocol) — an open standard for shipping tools as external servers so any agent can load them; our tools are hardcoded in Go instead.

08Our tool catalog

Eight tools, registered in order in tools.New(). The split between read-only and mutating is the backbone of the safety model.

Three design decisions worth understanding

1. Path confinement is enforced in Go, not in the prompt

Registry.resolve() joins, cleans, then computes the relative path from root and rejects anything starting with ... A model that asks to read ../../.ssh/id_rsa gets an error string, not a key. Never enforce security in the system prompt — prompts are advisory, code is not.

2. edit_file uses exact-string matching, not line numbers

Line numbers drift the moment anything above changes; models also hallucinate them. An exact-string match either hits or fails loudly. The uniqueness check ("appears 3 times; add more context") turns ambiguity into a correctable error instead of a silent wrong edit. This is the same design Claude Code uses, for the same reason.

3. ask_user is a tool, not a special case

Letting the model call for clarification is a genuinely elegant move. It turns "should I guess?" into a normal tool call the model decides to make, reinforced by the system prompt: "If the request is ambiguous… call ask_user BEFORE doing work. Do not guess on decisions that change the outcome." It is read-only, so it needs no approval — the interaction is the consent.

A note on the "bash" tool on Windows

We expose it to the model as run_bash but transparently dispatch to powershell -NoProfile -NonInteractive -Command on Windows. The model doesn't need to know. Keeping the tool surface stable while the implementation varies per platform is standard harness design — but it does mean the model may emit POSIX syntax on Windows, which the system prompt's OS line is there to discourage.

09Human in the loop — the permission system

An agent that can run arbitrary shell commands and overwrite files is, from a security standpoint, a remote code execution vulnerability you installed on purpose. The permission gate is what makes it acceptable.

   tool call arrives
          │
          ▼
   Mutating() ?  ── no ──► run immediately  (read_file, search, list_dir, ask_user)
          │
         yes
          ▼
   Preview(args)          ← builds a colored LCS diff, or shows the command
          │
          ▼
   scope := permScope(name, args)      ← "bash:git" / "file:main.go" / "server:api"
          │
          ▼
   already approved for this scope? ── yes ──► show preview, run
          │
          no
          ▼
   ┌──────────────────────────────────────────┐
   │  edit_file wants to proceed:             │
   │    - old line                            │
   │    + new line                            │
   │  [y] yes  [n] no  [a] always for main.go │
   └──────────────────────────────────────────┘
       y → run once      n → "User declined…" back to the model
       a → allowed[scope] = true for the rest of the session

The clever part: scoped approval

"Always allow" is where most agent tools get dangerous, because it usually means "never ask about this tool again" — approve one git status and you've approved rm -rf. permScope() narrows the grant:

Tool callScope key"Always" actually means
run_bash("git status")bash:gitall git commands — not rm, not curl
edit_file("main.go", …)file:main.goedits to that one file
run_server("npm run dev")server:devthat one named server

It is derived from the first word of the command, so it is a heuristic, not a sandbox — bash:git still covers git push --force. But it converts a blanket grant into a bounded one, which is the right shape of the tradeoff for a local dev tool.

Denial is feedback, not failure

A declined tool returns "User declined this action. Do not retry it; consider an alternative or ask what to do." The wording is deliberate: without "do not retry", models loop on the same rejected call. That sentence is a bug fix written in English.

Terminology

Human-in-the-loop (HITL) — a human approves consequential actions. Guardrails — the constraints around what the model may do. Sandboxing — isolating execution (containers, VMs). Autonomy level — how much runs without asking; ours is "approve mutations, auto-allow reads", with per-scope escalation. Blast radius — how much damage one bad action can do; path confinement and scoped approval both shrink it.

10Context window management & compaction

internal/agent/compact.go

Because history is re-sent in full every turn (§2), an unmanaged agent dies of its own success: the longer it works, the more it costs, until it hits the context ceiling and hard-fails. We use two defenses at different timescales.

Defense 1 — clamping (every tool result)

const maxToolResultInHistory = 24000

func clampForHistory(s string) string {
    if len(s) <= maxToolResultInHistory { return s }
    return s[:maxToolResultInHistory] +
      "\n… (truncated in history to save tokens; re-read a specific section if you need more)"
}

A 180 KB file read once would otherwise be re-uploaded on every subsequent turn for the rest of the session. Two details matter: the full result still goes to the transcript on disk (we lose nothing for debugging), and the truncation notice tells the model what to do about it — re-read a narrower section. A silent truncation would make the model reason about data it can't see.

Defense 2 — compaction (when the context gets big)

Once a turn's measured prompt_tokens crosses 60,000 — overridable with CLAUDE_MINI_COMPACT_AT — we fold old history into a summary.

The threshold pulls two ways

This is a cost/context tradeoff, and the right answer depends entirely on where inference happens.

On a caching provider, compact late. Compaction rewrites the prefix and invalidates the cache, so the next turn pays full price. Since the cached re-send was nearly free, compacting early is actively expensive.

On local CPU inference, compact early. Prompt processing is the entire bottleneck — measured at ~15 tok/s on a laptop with no usable GPU, meaning a 20k-token turn spends 22 minutes reading the prompt before emitting a single token. There, every token you can drop is worth more than any cache.

Same variable, opposite directions. That is why it is a knob and not a constant.

  BEFORE (crossed 60k):
  [ system | user₁ assistant tool tool | user₂ assistant tool | user₃ assistant tool | user₄ … ]
    keep      └──────────── summarize these ────────────┘   └──── keep verbatim ────┘
                                                              (last 2 user turns)
  AFTER:
  [ system | assistant:"[earlier conversation compacted]\n\n" | user₃ … | user₄ … ]

Three properties make this safe:

  • The cut lands on a user-message boundary. compactionCut() finds user-message indices and cuts at the N-th from the end. Cutting anywhere else could split an assistant's tool_calls from its tool results and break the invariant from §4.
  • The system prompt is never touched. history[0] is preserved explicitly.
  • Failure is a no-op. If the summarizer call errors or returns empty, we return without modifying history. Running slightly over budget beats silently destroying context.

The summarizer is a second, separate LLM call with its own mini system prompt and no tools. It is told exactly what to preserve: "the user's goals, files read or changed, key decisions and findings, commands run and their outcomes, and what still remains to be done." That list is the design — it keeps the plan and drops the transcript.

Terminology

Compaction / context compression — summarizing old turns to free tokens. Rolling / sliding window — just dropping the oldest messages (lossier; we don't do it). Summarization memory — the LangChain name for this pattern. Lost in the middle — the empirical finding that models attend worse to content in the middle of a long context, which is a second reason to compact rather than just grow. Context rot — accumulated stale/irrelevant context degrading answer quality.

We get real counts by sending stream_options: {include_usage: true}, which makes the provider append a final usage chunk. Output tokens are typically 3–5× more expensive than input, which is why our defaults are $0.60 in / $2.20 out per million (overridable via MINI_PRICE_IN / MINI_PRICE_OUT).

Cached tokens are the only proof caching works

Usage now also parses the cache fields both dialects report — OpenAI's prompt_tokens_details.cached_tokens and Anthropic's cache_read_input_tokens/cache_creation_input_tokens — and the footer surfaces the hit rate when there is one:

↑ 77.3k in (448 cached, 1%) · ↓ 648 out · 78.0k total · ~$0.0476 (est.)

Its absence is the diagnostic. No figure means the endpoint reported no cache hit, whatever the request asked for — which is exactly how you find out whether a given gateway passes cache directives through. A 1% hit rate, as above, means caching is effectively not working on that path.

Two different token numbers on screen

Worth knowing, because they disagree on purpose:

  • The spinner's live number is an estimate: base + len(runes)/4. The real count doesn't exist until the stream ends, and a progress indicator needs a number now.
  • The footer after each task is the exact figure the provider billed, accumulated in Cost.

Estimate while running, truth when done — a reasonable pattern whenever the authoritative number arrives late.

12Transcripts, resume & undo

internal/session/session.go

The transcript (JSONL)

Every session appends to .mini_agent/sessions/YYYYMMDD-HHMMSS.jsonl — one JSON object per line:

{"ts":"2026-09-20T10:02:11Z","kind":"user","payload":"add a test…"}
{"ts":"…","kind":"assistant","payload":{"role":"assistant","tool_calls":[…]}}
{"ts":"…","kind":"tool_result","payload":{"name":"read_file","result":"…"}}
{"ts":"…","kind":"compaction","payload":{"summarized_messages":14}}

JSONL is chosen for a reason: append-only, crash-safe (a truncated last line just gets skipped), and streamable without loading the file. Crucially it stores the full, unclamped tool results — the transcript is the ground truth, history is the lossy working set.

Resume — replaying a log into a valid conversation

/resume finds the most recent other transcript (timestamp filenames sort lexically = chronologically), reads the records, and rebuilds history after the system prompt.

The hard part is re-pairing. Tool results are logged flat, with no tool_call_id. Resume() reconstructs the pairing positionally: it holds the last assistant message's tool_calls as pending and consumes them in order with an index pi. Then the finishing move:

// Drop a dangling final assistant turn with unanswered tool calls.
if lastAssistant >= 0 && pi < len(pending) {
    a.history = a.history[:lastAssistant]
}

If the previous session was killed mid-tool, that assistant message has tool_calls with no results — an instant 400 on the next request (§4). So we amputate it. Better to lose one turn than to resume into a permanently broken conversation.

Undo — a shadow stack of file contents

Before every write, RecordWrite() snapshots the file's current bytes (and whether it existed at all) onto a stack. /undo pops one: restore the old bytes, or delete the file if it didn't exist before. In-memory only, single-level-per-pop, and independent of git — deliberately, since the project may not be a repo and the user may have uncommitted work.

13Interrupts & the invariants they must not break

Pressing Esc mid-stream is a small feature with a surprisingly deep design, because a cancel that leaves history malformed bricks the session.

Cancellation plumbing

Run() creates runCtx, cancel := context.WithCancel(ctx). The escWatcher goroutine (installed from main.go, only when we're on a real TTY) opens the keyboard, waits for Esc, and calls cancel(). That context is threaded into the HTTP request, so the in-flight stream aborts immediately.

The stdin handoff

The watcher is installed only around the streaming call and released the moment it returns:

release := a.watch(cancel)      // keyboard grabs stdin
msg, usage, err := a.client.Stream(…)
release()                       // keyboard lets go
// …now the tool phase can safely use stdin for y/n/a prompts

Two readers on one stdin is a classic terminal bug — keystrokes vanish into the wrong consumer. Scoping the watcher to exactly the window where no prompt can appear eliminates it structurally.

Interrupting mid-tool-loop

This is the part that protects the invariant. If the user cancels while three tool calls are queued, we do not bail out. We iterate all of them, and for any that didn't run we push a synthetic result:

case interrupted || runCtx.Err() != nil:
    interrupted = true
    result = "[interrupted by user before this tool ran]"

Every tool_call gets its matching tool message. History stays valid, so the user can type more instructions and the model picks up exactly where it stopped — including knowing which of its own requests never executed. Pause, not abort.

14Failure handling — the difference between a demo and a tool

Everything above assumes the model behaves. It often doesn't. A weak model mis-escapes JSON, retypes a tab as spaces, or repeats a doomed action forever. Each of those produced a real, observed failure, and each is answered in a different layer.

The governing rule

A tool error is never a crash and never a bare "it failed". It is a message written for a reader who cannot see our source code, whose only chance to recover is the sentence we hand back. Every error string below is engineered to be acted on.

Layer 1 — Malformed tool arguments

internal/llm/sanitize.go

Weaker models emit raw newlines and tabs inside JSON string literals, which makes arguments unparseable. Worse, an unserializable tool call that reaches history poisons every later request (§4's invariant). So repair happens at the boundary, before it is ever stored:

SanitizeToolCalls(&out)   // called in streamOnce, before the message is returned

RepairArguments returns valid JSON unchanged, escapes stray control characters inside strings and returns that if it now parses, and otherwise substitutes a marker object. The marker turns an unrecoverable payload into a correctable error rather than a permanently broken conversation, and the agent answers it with the escaping rules spelled out: newline as , tab as , quote as \", backslash as \.

Layer 2 — Edits that nearly match

internal/tools/file.go

The most expensive failure this agent had: edit_file returning old_string not found, the model re-reading the same file, guessing again, and looping. Six retries and 40k tokens on one edit. Nearly every miss is whitespace — the model retypes a tab-indented line with spaces.

Two changes, in order of preference:

  • Accept it. If the block matches once indentation is normalized and the match is unambiguous, apply it, re-indent the replacement to the file's own style, and say so in the result so the substitution is visible rather than silent.
  • Explain it. If it still cannot match, name the near-match line, what differs, and show the real text with tabs made visible:
old_string not found in login_controller.go, but line 140 matches once whitespace
is ignored — this file indents with TAB characters, and old_string uses spaces.
The file has:
  		access, err := guviLib.LoginWithGUVI(email, pwd)
Copy the text byte-for-byte from read_file (a tab must be written 	 in JSON),
or use write_file to replace the whole region.

Two supporting changes remove the reason to re-read at all: write_file and edit_file now return a diff of what landed, and read_file is paged (offset/limit, line-numbered, numbers marked display-only) so a model can pull one function instead of a whole file.

Layer 3 — Doomed repetition

internal/agent/agent.go

Better messages help a model that can correct itself. Nothing helps one that can't — and nothing in the loop stopped it from trying forever. So identical failures are counted:

key := tc.Function.Name + "" + tc.Function.Arguments
a.failed[key]++

The second identical failure appends a STOP: directive naming concrete alternatives (write_file, a smaller fragment, ask_user) and explicitly forbidding the re-read-and-retry pattern. The third demands BLOCKED. A changed argument counts as a new attempt, so genuine self-correction is never punished, and counts reset each task.

This converts an open-ended spin into at most two attempts and a forced change of tactic — the difference between failing in thirty seconds and burning five minutes.

Terminology

Self-correction — the model fixing its own call from an error message. Graceful degradation — accepting a near-miss instead of rejecting it. Loop / repetition detection — noticing the agent is stuck. Failing loudly — surfacing a problem where the cause is visible rather than three turns later. Poisoned context — one malformed message making every subsequent request fail.

Asking the provider what it actually serves

A model name is meaningless on its own — it is a menu item at a specific endpoint. (BaseURL, APIKey) is the account; Model is a string passed through. A hardcoded shortlist frozen at compile time therefore goes stale, and offers models the provider does not have.

So we ask, via the OpenAI-compatible discovery endpoint:

GET {baseURL}/models   →   {"data":[{"id":"…"}, …]}

Three things follow from having the real catalog. /model lists what the provider genuinely offers, with curated presets it serves floated to the top. A typed name the catalog does not contain is challenged before it is accepted, instead of surfacing turns later as an opaque API error. And switching provider lands on a model the new endpoint actually serves rather than silently inheriting the previous one's — the bug that let a Gemini model id carry over to a Google endpoint that had never heard of it.

Discovery is strictly best-effort: not every endpoint implements it and most require a valid key, so any error means "no catalog" and falls back to the built-in presets. Ids are kept verbatim — some providers namespace them (models/gemini-2.0-flash) and that prefix is part of what the chat endpoint expects.

The pasted-URL trap

Providers document their endpoint as the full …/v1/chat/completions path, so that is what people paste into /provider. But the client appends /chat/completions itself, producing a doubled path. normalizeBase strips the suffix on the way in — cheap insurance against a failure mode that, on at least one gateway, is silent (§5).

Prompt caching

Our request prefix is byte-stable by construction: the system prompt has no timestamp, tool schemas are fixed, history is only ever appended to, and a clamped tool result stays identical forever. That is exactly what a cache keys on. Marking breakpoints is opt-in via CLAUDE_MINI_CACHE=1, deliberately — a breakpoint sends message content as a structured block instead of a plain string, and an endpoint that does not understand that shape rejects the whole request. Since no gateway advertises whether it forwards cache directives, it stays something you turn on and confirm against the cached figure in the footer.

Config precedence is layered, highest first: environment variables (CLAUDE_MINI_BASE_URL / _API_KEY / _MODEL) → saved config file → built-in defaults. Env-first is what makes the tool usable in CI without writing to disk. A .env file in the project is loaded at startup but never overrides an already-set variable.

Terminology

Inference provider — whoever runs the model weights. Model gateway / aggregator — one API fronting many providers (OpenRouter, OpenAdapter). Local inference — the model runs on your machine (Ollama, llama.cpp, vLLM). OpenAI-compatible — exposes /v1/chat/completions with the same schema; the industry's lingua franca. Open-weights model — downloadable weights (Llama, Qwen, DeepSeek) vs API-only (GPT, Claude, Gemini). Quantization — shrinking weights to 8/4 bits so they fit in consumer RAM; why qwen2.5-coder runs on a laptop.

Why no RAG?

Worth being able to defend, because people will ask. RAG guesses which snippets might be relevant and injects them upfront. Agentic search lets the model look things up itself, iteratively, based on what it just learned: search for a symbol → read_file the hit → follow an import → search again. For a codebase — where structure is explicit and grep is exact — agentic search is more precise and needs no index, no embedding pipeline and no staleness story. This is the same choice Claude Code makes. RAG earns its keep for fuzzy natural-language corpora, not for code.

The honest weakness

Every behavioral decision in our system prompt and tool descriptions was made by intuition and anecdote. Without an eval suite — a fixed set of tasks scored automatically — there is no way to know whether the next prompt tweak helps or hurts. In production agent work, evals are the difference between engineering and superstition. It is the single most valuable thing this project is missing.

18The course behind this project

If someone asked "what did you actually learn building this?", here is the syllabus, in the order the concepts build on each other.

Module 1 — The model is a text function

Stateless. No memory, no tools, no side effects. It maps a message array to more text. Everything else is the harness. §1, §2

Module 2 — Conversation state is your problem

History lives on the client and is re-sent in full every turn. That single fact generates the cost curve, the context ceiling, and the structural-validity rules. §2, §4

Module 3 — The chat protocol

Four roles, the tool_call_id pairing invariant, SSE deltas, and why arguments arrives as a string. §4, §5

Module 4 — Prompting as programming

Identity, environment, policy, output contract. Behavior is specified in English and it is real engineering — every sentence in our prompt exists to prevent an observed failure. §6

Module 5 — Tools turn text into action

Advertise a JSON Schema, receive a request, execute, report back. The description is the contract. Errors are feedback, not crashes — self-correction is what makes an agent useful. §7, §8

Module 6 — The agentic loop

Call → tool calls? → execute → append → repeat. Termination on empty tool calls. This is the whole of "agents". §1, §3

Module 7 — Safety is code, not prose

Path confinement, mutating/non-mutating split, diff previews, scoped approval. Enforce in Go; never rely on the prompt for security. §8, §9

Module 8 — Context economics

Clamp results, compact old turns, cut on safe boundaries, never drop the system prompt, fail soft. §10, §11

Module 9 — Durability

Append-only transcripts, resume with pairing repair, an undo stack independent of git, and interrupts that pause rather than corrupt. §12, §13

Module 10 — Failure is the design

Repair malformed arguments at the boundary; accept a near-miss and say you did; make every error a sentence the model can act on; count repeats and force a change of tactic. A harness is judged by how it behaves when the model is wrong, because it usually is. §14

Module 11 — Portability

One standard protocol, three swappable strings, layered config — plus asking the provider what it actually serves rather than trusting a hardcoded list. Same code from a cloud frontier model to a laptop running Ollama. §15

The one-paragraph version

claude-mini keeps a growing array of chat messages in memory. Each turn it POSTs that whole array — plus eight JSON-Schema tool definitions — to an OpenAI-compatible endpoint, and reassembles the streamed SSE deltas into one message. If that message contains tool calls, it parses their JSON arguments, shows the human a diff and asks permission for anything mutating, executes real Go functions against the filesystem and shell, appends each result as a tool message, and loops. When the model replies with prose and no tool calls, the task is done. Along the way it clamps oversized results, summarizes old turns once context passes 60k tokens, tracks exact token usage from the provider, writes every event to an append-only JSONL transcript, keeps an undo stack of file contents, and handles Esc as a pause that leaves the conversation structurally valid. When the model misbehaves — malformed JSON arguments, an edit whose indentation does not match, the same doomed call issued over and over — it repairs, tolerates or escalates rather than crashing or spinning. And because it asks each provider which models it really serves, the same binary points at a frontier API or a laptop with equal confidence. That's the whole backend.
